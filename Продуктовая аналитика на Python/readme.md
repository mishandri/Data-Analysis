# Продуктовая аналитика на Python

Четыре прикладных задачи на чистом Python, без pandas. Общая идея всех четырёх: данные приходят в неудобном виде, и половина работы состоит в том, чтобы их правильно прочитать.

## Стек

`csv`, `re`, `datetime`, `collections`, `ast`, `decimal`, `dataclasses`, `pathlib`. Внешних зависимостей нет вообще, включая pandas.

## Почему без pandas

Pandas прощает разбор и прячет именно то, что здесь и нужно понять. Чтобы разобраться, как устроены когорты, чем n-day отличается от rolling и почему словарь в наборе данных использовать нельзя, сначала надо один раз написать это руками.

Плюс на таких объёмах, от 1000 до 5000 строк, стандартная библиотека работает так же быстро, а ноутбук остаётся читаемым: видно, что происходит с каждой записью.

## 01. Продуктовые метрики

1000 пользователей, 20 734 входа, год 2021.

| Метрика | Значение |
|---|---|
| Retention day 1 | 0.4660 |
| Retention day 7 | 0.4820 |
| Retention day 14 | 0.4760 |
| Retention day 30 | 0.2410 |
| Rolling day 14 | 0.9780 |
| Lifetime, интеграл n-day | 14.804 |
| Churn day 29 | 0.509 |
| MAU декабрь | 133 |
| WAU, 25-31 декабря | 84 |
| DAU, 31 декабря | 47 |
| Средний MAU за год | 102.58 |
| Средний WAU за 53 недели | 89.87 |
| Средний DAU за 365 дней | 40.56 |

Что показала работа:

- **n-day и rolling отвечают на разные вопросы.** На 14-й день это 47.6% против 97.8%. Большинство возвращается, но не в конкретный день. Путать их приводит либо к панике, либо к ложному спокойствию.
- **Lifetime зависит от того, какая кривая интегрируется.** 14.80 в n-day версии против 28.33 в rolling, почти вдвое. Определение надо указывать рядом с числом.
- **Правая цензура ломает свежие когорты.** На 30-м дне 43 из 84 декабрьских пользователей просто не дожали до этого дня, поэтому метрика показывает 0.241 вместо реального удержания. Любой свежий отчёт по удержанию надо начинать с этой проверки.
- **Средние скрывают разброс.** Day 7 по когортам от 0.28 в феврале до 0.60 в январе, churn от 0.36 до 0.80.

Технически: словарь для регистраций использовать нельзя, повторная запись с тем же `user_id` затрёт предыдущую. Номер недели строится через `isocalendar()`, а не `%W`, иначе первая и последняя недели года попадут в один ключ.

## 02. Логи автопродлений

47 строк лога за неделю, три вида записей: попытка списания, ошибка, итог за день.

| Метрика | Значение |
|---|---|
| Попыток списания | 32 |
| Успешных | 24 |
| Ошибочных | 8 |
| Доля успешных | 0.75 |
| Подписчиков на 9 октября | 23 |
| Накопленное среднее | 22.14 |
| Накопленная медиана | 22 |

Что показала работа:

- **`INFO` в логе пишется на каждую попытку, включая неуспешные.** Это прямо сказано в ТЗ, но по виду лога не очевидно: строка выглядит как обычное успешное обновление. Считать успех и ошибку раздельно нельзя, доля успеха всегда завышена. В исходной версии это давало бы 1.0 вместо 0.75.
- **Дата не берётся срезом по индексу.** `INFO | ` длиннее `ERROR | ` на символ, и `line[7:17]` на ERROR-строках даёт `2022-10-0`, на чём `strptime` падает. Уровень логирования в реальной системе меняется, поэтому даты достаются поиском по разделителю.
- **Дни недели по одной неделе читать нельзя.** На каждый день недели ровно одно наблюдение, вся разница это шум выборки.

Технически: дубли итоговой строки за день берутся как максимум, а не последнее значение, иначе перезапись затёрла бы настоящий итог. Медиана написана руками с проверкой на чётность длины.

## 03. Рекламные кампании

1020 кампаний, 5 платформ, 8 городов, год 2022.

| Метрика | Значение |
|---|---|
| Лучшая платформа по ср. конверсий | Instagram, 107.83 |
| Лучшая платформа по доходу на бюджет | Instagram, 0.677 |
| Лучшая платформа по конверсиям на клик | Telegram, 0.1966 |
| Худшая платформа по доходу на бюджет | Яндекс, 0.544 |
| Лучший город по доходу на бюджет | Казань, 0.694 |
| Худший город по доходу на бюджет | Калуга, 0.512 |
| Дней без запусков за год | 18 |

Что показала работа:

- **Среднее число конверсий и доход на рубль бюджета дают разные ответы.** Яндекс худший по первому и предпоследний по второму, потому что кампании дорогие. Для решения о бюджете нужен второй показатель.
- **Разброс между городами шире, чем между платформами:** 36% против 24%. География оказалась значимее выбора площадки.
- **Москва на Instagram получает 9.11% бюджета, последнее место из восьми**, при среднем результате. Казань получает 12.22% и отдаёт лучше всех.
- **Все ROI меньше единицы** на любой платформе и в любом городе. Либо в столбце «доход» не выручка, либо реклама действительно убыточна. Этот вопрос надо задать до выводов о перераспределении.

Технически: числа приходят строками, часть с плавающей точкой, `int("507.0")` падает, нужен `float` с последующим `int`. Генератор пропущенных дат строит полный ряд между min и max и вычитает дни с запусками.

## 04. Пользовательские сессии

5283 сессии, 1000 пользователей, май-июнь 2023. Внутри CSV лежит вложенная структура с экранированными кавычками.

| Метрика | Значение |
|---|---|
| Среднее до конверсии | 467.24 сек |
| Медиана до конверсии | 364 сек |
| Конверсий быстрее 30 секунд | 75, 7.4% |
| Средняя длительность сессии | 901.35 сек |
| Медиана длительности | 900 сек |
| Максимальная длительность | 1800 сек |
| Сессий на пользователя | 5.28 |
| Заходов в день на пользователя | 4.77 |
| Заходов в день на активный день | 1.11 |
| Страниц в сессии | 8.17 |
| Конверсия сессий | 19.23% |
| Конверсия пользователей | 59.90% |

Что показала работа:

- **`split(",", 1)` обязателен.** Внутри сессии десятки запятых, обычный split развалит строку.
- **Это не JSON, хотя выглядит как JSON.** Даты записаны без кавычек, `json.loads` падает, нужен `ast.literal_eval`.
- **Конверсия сессий 19.2% против конверсии людей 59.9%.** Разрыв в три раза означает, что конвертирующиеся заходят чаще и конвертируются почти в каждой сессии. 80% людей не конвертируются вообще. Ориентироваться надо на пользователей: усреднение по сессиям занижает потенциал втрое.
- **Артефакты видны только если искать.** 7.4% конверсий зафиксированы раньше первого перехода, длительность упирается ровно в 1800 секунд. Оба ограничения пришли из генератора данных.

## Что общего у четырёх задач

Главная работа везде одинаковая и она не в формуле:

1. **Прочитать данные как есть.** В логе `INFO` пишется на каждую попытку, в сессиях JSON лежит внутри CSV, в кампаниях числа приходят строками с точкой.
2. **Найти границы применимости.** Свежие когорты в retention, одна неделя в днях недели, 1800 секунд в длительности сессии.
3. **Не поверить первому числу.** 86% просрочек в одном из соседних проектов выросли из-за размножения строк при join. Почти всегда сначала надо проверить, что считаешь то, что думаешь.

Именно на этом чаще всего ломаются junior-решения: метрика посчитана, код работает, а цифра в отчёте означает не то, что написано в заголовке.
