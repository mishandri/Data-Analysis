# Ассортиментный анализ аптечной сети

Один и тот же набор данных, два инструмента. SQL даёт масштабируемый расчёт, который пойдёт в BI, Excel воспроизводит ту же методику в том файле, где работает закупка.

Источник один: таблица `sales` с чеками, поля `dr_apt`, `dr_nchk`, `dr_dat`, `dr_ndrugs`, `dr_kol`, `dr_croz`, `dr_czak`, `dr_sdisc`.

## Стек

PostgreSQL: CTE, оконные функции с накопительной суммой, `CROSS JOIN`, `LEFT JOIN`, self-join.

Excel: сводные таблицы, формулы, условное форматирование.

## Файлы

**SQL**

- `01. ABC-анализ.sql`. Товары по трём метрикам сразу: количество проданных единиц, прибыль позиции, выручка.
- `02. XYZ-анализ.sql`. К первому запросу добавлена оценка стабильности спроса, на выходе матрица ABC × XYZ.
- `03. Сочетаемость товаров.sql`. Какие товары чаще покупают в одном чеке.
- `04. Таблица продаж.sql`. Кросс-таблица «товар × аптека» со всеми комбинациями, включая нулевые продажи.

**Excel**

- `Excel/ABC-анализ в Excel.xlsx`. Сводные таблицы и формулы, ABC по выручке, количеству и частоте.
- `Excel/ABC_XYZ-анализ в Excel.xlsx`. Добавлен XYZ по стабильности спроса, сводные таблицы ABC и XYZ.

## Метрики и формулы

Формулы одинаковые в обоих инструментах:

```
выручка = SUM(dr_kol * dr_croz - dr_sdisc)
маржа   = SUM((dr_croz - dr_czak) * dr_kol)
```

Плюс частота продаж, то есть количество чеков с товаром, и доля товара в выручке дня.

Прибыль считается с вычетом закупочной стоимости и скидок, поэтому по ней всегда меньше выручки.

## ABC-анализ

Классификация делается одним проходом оконной функцией, без промежуточных таблиц:

```sql
SUM(amount) OVER (ORDER BY amount DESC) / SUM(amount) OVER () <= 0.8  → 'A'
                                                                        <= 0.95 → 'B'
                                                                                 → 'C'
```

Накопительная доля считается сразу по трём метрикам, и на выходе у каждой позиции есть `amount_abc`, `profit_abc` и `revenue_abc`.

Так видно расхождение между метриками: позиция может быть в A по выручке и в C по количеству. Для закупщика это разные сигналы, поэтому три буквы в одной строке полезнее одной категории. В Excel тот же приём даёт категории вида `AAA`, `AAB`, `AAC`.

## XYZ-анализ

Спрос сворачивается по товару и неделям (`YYYY-WW`), дальше коэффициент вариации:

```
CV = STDDEV(kol) / AVG(kol)
X ≤ 0.1    Y ≤ 0.25    Z > 0.25
```

## Слабое место Excel-версии

В SQL-версии стоит `HAVING COUNT(DISTINCT ym) >= 4`. Товары с короткой историей не классифицируются вовсе и получают `NULL` в итоговой выборке.

Без этого фильтра у новичка ассортимента была бы категория Z, хотя это не нестабильный спрос, а отсутствие данных.

В Excel такого фильтра нет. Часть позиций получает Z просто из-за того, что данных мало, и при визуальном чтении такой товар выглядит как «спрос непредсказуем». Перед использованием Excel-версии этот столбец надо фильтровать вручную, либо переносить расчёт в SQL.

Это и есть главный довод в пользу SQL-реализации: метод с фильтрами и проверками переносится один раз, а не каждый раз заново в каждой ячейке.

## Сочетаемость

CTE `soch` убирает повторы товара внутри чека. Иначе пара «A+A» засчиталась бы как совместная покупка, а это артефакт одного чека, а не паттерн поведения.

Дальше self-join с условием `s1.dr_ndrugs < s2.dr_ndrugs`. Неравенство строгое, поэтому пары A+B и B+A схлопываются в одну строку, а товар с самим собой не попадает в выдачу.

Джойн идёт сразу по трём ключам: аптека, номер чека и дата. Если склеивать только по номеру чека, одинаково пронумерованные чеки разных дней и аптек объединятся в одну фиктивную покупку.

## Таблица продаж

`CROSS JOIN` списка товаров на список аптек даёт полный декартов набор комбинаций, `LEFT JOIN` поверх возвращает `NULL` там, где продаж не было. Ноль и отсутствие строки в сводной таблице означают разное, и матрица сохраняет эту разницу.

## Итог

Один набор инструментов, оконные функции, CTE, self-join и `CROSS JOIN`, решает четыре несвязанные задачи без Python. Плюс границы применимости методов: фильтр по числу периодов в XYZ, дедупликация перед self-join, полнота матрицы через `CROSS JOIN`.

Excel-версия полезна как сверка: если SQL и Excel дают разные категории на одном срезе, значит в одной из реализаций ошибка в логике, а это дешевле поймать на тираже, чем на готовом отчёте.
