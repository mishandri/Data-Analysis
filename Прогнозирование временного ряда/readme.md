# Прогнозирование временного ряда платежей

ClickHouse, `stochasticLinearRegressionState`, SGD. Данные из таблицы `payment`, период январь-июль 2024. Всё считается внутри базы, данные наружу не выгружаются.

## Задача

Построить прогноз ежедневной суммы успешных платежей и оценить, стоит ли он того, чтобы его использовать.

## Стек признаков

Суточные суммы успешных платежей, дата, линейный тренд, логарифм суммы, бинарные индикаторы дней недели от `DoW1` до `DoW7`.

Логарифм цели сделан не для красоты. Суммы платежей распределены мультипликативно и имеют тяжёлый хвост. После логарифма мультипликативные эффекты становятся аддитивными, выбросы перестают раздувать дисперсию, и SGD не переобучается на единичных крупных днях. Обратное преобразование `exp()` делается на этапе предсказания.

Тренд нормализован в [0, 1]. Без этого SGD не сойдётся, ему нужен масштаб входов.

## Разделение данных

Обучение январь-июнь, тест июль. Разделение строго по времени.

Случайное перемешивание в задаче прогноза недопустимо: будущие значения попадают в обучение, модель видит то, чего не будет, и качество выходит завышенным. Это самая частая ошибка в прогнозных задачах, и на коротких рядах она даёт красивый, но бессмысленный результат.

## Обучение

`stochasticLinearRegressionState(0.1, 0.0, 5, 'SGD')`, то есть скорость обучения 0.1, нулевая L2-регуляризация, батч 5, метод SGD.

Состояние модели сохраняется в таблице `payment_model`, а не пересоздаётся в каждом запросе. Поэтому обучение можно продолжить на новых данных и не начинать с нуля.

## Baseline

Отдельный запрос `payment_baseline` строит два простых прогноза на той же обучающей выборке:

**Вчерашнее значение.** Наиболее естественный baseline для платежей: сумма сильно зависит от дня недели и медленно дрейфует, поэтому вчерашнее значение обычно лучше среднего за месяц.

**Среднее за последние 7 дней.** Сглаживает недельную сезонность, но уже не ловит её.

Оба считаются только по январю-июню. Значения факта из июля не подглядываются ни в одном из них, иначе сравнение получилось бы нечестным.

## Метрики

Используются две, обе в агрегированном виде:

- **WAPE** = сумма абсолютных ошибок делённая на сумму факта. Устойчива к дням с нетипично большим отклонением, в отличие от среднего процента ошибки по каждому дню.
- **MAE** = средняя абсолютная ошибка в рублях. Показывает размер ошибки в деньгах, а не в процентах, по ней удобно прикидывать последствия.

Формулы в SQL:

```sql
abs(fact - forecast) / fact  -- погрешность по дню, суммируется
sum(err) / sum(fact)          -- и превращается в WAPE
```

## Почему без baseline качество не оценить

На платежах «вчерашнее значение» почти всегда даёт маленькую ошибку, потому что дневные суммы меняются плавно. Модель, которая ничего не выучила, а просто повторяет вчера, на таком ряду будет выглядеть почти идеально.

Поэтому итоговый запрос выводит три строки в одном формате: модель, вчерашнее значение, среднее за неделю. Читать надо так: если WAPE модели хуже хотя бы одного baseline, прогноз не годится, каким бы сложным он ни выглядел. Если лучше обоих, но разница в пределах 2-3 процентных пунктов, выигрыш скорее случайный и в продакшен лучше брать baseline, он дешевле и предсказуемее.

Плюс последний запрос выводит ошибку по каждому дню июля, чтобы видеть структуру провалов, а не только итог.

## Почему не выносить в Python

Обработка не покидает базу, трафик между системами сведён к минимуму, объёмы данных не упираются в память машины аналитика. Состояние модели лежит рядом с данными.

Для платёжных данных это ещё и требование: их не нужно перемещать туда, где им не место.

## Что стоит проверить перед использованием

Прогноз построен на семи месяцах и проверен на одном. Этого мало для вывода о пригодности модели: июль может оказаться нетипичным месяцем, и тогда результат скажет о погоде, а не о качестве.

Перед выводом в бой стоит прогнать скользящее окно, например обучение на шести месяцах и проверка на следующем, повторив несколько раз. Тогда будет видно, устойчив ли результат или это разовая удача. И обязательно смотреть на ошибку по месяцам, а не только на итоговую.
