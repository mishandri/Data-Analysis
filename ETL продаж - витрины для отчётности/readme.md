# ETL продаж: из плоской выгрузки в три витрины

Python 3, стандартная библиотека. Pandas не используется.

## Задача

Плоская выгрузка кассового ПО разбирается на три витрины для отчётности: отфильтрованные строки, агрегаты по месяцам, агрегаты по товарам. Запуск по расписанию, без участия человека.

Постановка задачи целиком в [ТЗ.md](ТЗ.md).

## Стек

`csv`, `dataclasses`, `datetime`, `decimal`, `pathlib`, `collections`. Внешних зависимостей нет.

## Данные

`sales_data.csv`, 1000 строк, период с августа 2022 по май 2023, 10 товаров.

```csv
id,date,amount,product
1,2023-04-25,35.21,Product 6
2,2022-08-31,359.19,Product 9
```

## Как устроен код

```
read_sales        чтение CSV в список Sale
filter_by_date    отбор по периоду, включительно
filter_by_amount  отбор по диапазону сумм, включительно
aggregate         сумма и количество по произвольному ключу
write_csv         запись витрины, папки создаются при необходимости
build             пайплайн целиком
```

`build` принимает параметры периода и диапазона и возвращает сводку в словаре, поэтому её можно вызывать с разными настройками, не меняя код ниже.

## Решения, которые стоит отметить

**Деньги в `Decimal`, а не в `float`.** Двоичное представление не хранит десятичные дроби точно. На сумме в сотни тысяч копейки набегают, и итог перестаёт сходиться с суммой строк. `Decimal` хранит число десятичным, сложение точное.

**Округление `ROUND_HALF_UP`.** В Python по умолчанию банковское округление `ROUND_HALF_EVEN`, где 0.5 уходит к чётному. В отчётности от этого суммы строк расходятся с итогом на копейку.

**`Sale` это `frozen=True`.** Запись из выгрузки после чтения не меняется. Заморозка запрещает случайную правку и заодно делает объект хешируемым, если понадобится класть его в множество.

**Даты приводятся один раз, при чтении.** Дальше по коду только `datetime`, сравнение идёт напрямую. Если бы в выгрузке смешались форматы дат, падение случилось бы на первой же строке чтения, а не где-то в середине агрегации.

**Фильтры складываются.** `filter_by_date` и `filter_by_amount` независимы и работают с одним типом на входе и выходе, поэтому любой можно вызвать первым, а можно оба не вызывать.

**Пустой результат проверяется.** Если фильтры дают ноль строк, средний чек считать не от чего. В коде это обработано, иначе деление на ноль.

## Что видно из результата

Июнь даёт максимум и по количеству чеков, и по сумме, март наоборот минимум. Но сказать, что это рост бизнеса, нельзя: июнь это последний месяц окна плюс в него целиком попали самые крупные чеки. Для вывода о тренде нужен ряд по всем двенадцати месяцам, а не срез по одному полугодию.

Распределение по товарам плоское: от 20 953 до 32 072, разница в полтора раза при десяти позициях. Ни один товар не выделяется настолько, чтобы о нём стоило писать отдельно. В данных синтетическая структура, такую картину даёт генератор, а не реальная продажа.

