# Выгрузка данных из API сайта в PostgreSQL

Python, `requests`, `psycopg2`, `logging`, `smtplib`, `ssl`, PostgreSQL, API Яндекс.Диска.

ТЗ в [ТЗ_проекта.md](ТЗ_проекта.md).

## Задача

В LMS корпоративного клиента встроен редактор кода, он же грейдер. Каждый день тысячи студентов решают задачи, запросы улетают на сервер. Аналитике клиента нужно забирать, кто какие задачи решал, когда была попытка и была ли она успешной.

```
API → APIClient.fetch_data → валидация → ConnectDB → PostgreSQL
                                              ↓
                                    отчёт xlsx → Диск → письмо
```

## Структура БД

Таблица создаётся один раз, скрипт только пишет данные, поэтому DDL вынесен из кода в `create_table_users.sql`.

Ключевое в схеме это составной уникальный ключ:

```sql
CONSTRAINT users_attempt_unique UNIQUE (user_id, created_at, attempt_type)
```

Идентификатора попытки в ответе API нет, но `user_id`, `created_at` и `attempt_type` вместе определяют попытку однозначно. Повторный запуск скрипта в тот же день без такого ключа удваивает все строки: ошибка не падает, не логируется и обнаруживается через месяц, когда DAU в отчёте вдруг вырос вдвое.

Плюс индекс по `created_at`. Ежедневный отчёт за вчера без него делает последовательное сканирование всей таблицы, а она растёт каждый день.

## Классы

`ConnectDB` это синглтон. За день загружаются сотни тысяч записей, и одно соединение на процесс здесь важнее, чем кажется: новое соединение на каждую запись означало бы нагрузку на сервер БД без всякой нужды.

`APIClient.fetch_data` ходит в API с параметрами `client`, `client_key`, `start`, `end`. Самая неприятная часть ответа это `passback_params`: три нужных значения лежат внутри строкового представления словаря, часть полей отсутствует, часть лишняя.

Запись с некорректными данными пропускается, и сам факт пропуска пишется в лог. Тихий drop здесь означал бы, что через месяц никто не сможет объяснить, почему в аналитике не хватает данных.

`YandexDisk` отвечает за выгрузку отчёта на Диск, метод `report` принимает имя файла.

## Отчёт и уведомление

Отчёт в xlsx выкладывается на Яндекс.Диск, потом уходит письмо на почту через `smtplib` с SSL и `EmailMessage`. Заказчик получает результат без доступа к базе и без установки чего-либо у себя.

Пароли Диска и почты лежат в локальных файлах и в репозиторий не попадают.

## Про повторные запуски

Запись идёт через `ON CONFLICT DO UPDATE` по ключу `(user_id, created_at, attempt_type)`:

```sql
ON CONFLICT (user_id, created_at, attempt_type)
DO UPDATE SET
    oauth_consumer_key = EXCLUDED.oauth_consumer_key,
    is_correct = EXCLUDED.is_correct
```

Что это даёт. Скрипт запускается по расписанию и может быть перезапущен в тот же день: после сбоя, вручную, с двух разных машин. Без upsert повторный запуск удваивает строки, и через месяц никто не сможет объяснить, откуда взялся рост DAU.

Обновляются только те поля, которые приходят из API. Ключевые поля не трогаются, иначе Postgres посчитал бы их конфликтом.

В лог пишется `cursor.rowcount`, это число реально затронутых строк. При повторном запуске оно отличается от числа переданных записей, и по логу это видно без обращения к базе.
