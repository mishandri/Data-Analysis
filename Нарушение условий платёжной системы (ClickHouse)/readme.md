# Выявление нарушений условий платёжной системы (ClickHouse)

ClickHouse, оконные функции с `RANGE`.

## Условие задачи

Платёжная система ограничивает сумму: за 24 часа успешные платежи одного пользователя не должны превышать 20 000 000. Нужно найти операции, на момент которых лимит уже был превышен.

## Данные

| Поле | Тип | Что это |
|------|-----|---------|
| `account_id` | UInt64 | пользователь |
| `operation_id` | UInt64 | операция |
| `amount` | Decimal | сумма платежа |
| `operation_datetime` | DateTime | время операции |
| `status` | String | статус |

## Логика

Для каждой операции считается сумма и количество операций за предшествующие 24 часа. Границы окна: `interval_start` это время операции минус сутки, `interval_end` это время операции. Остаются те операции, где накопленная сумма превысила порог.

Сначала фильтруется `status = 'completed'`. Отменённые операции в условии лимита не участвуют, и оставлять их в расчёте нельзя.

## Настройки

Порог и окно вынесены в начало запроса как константы, чтобы правило лимита менялось без правки логики:

```sql
WITH
24 AS hours,
20_000_000 AS threshhold,
```

## Что отдаёт запрос

`account_id`, `amount` текущей операции, границы интервала, `interval_amount` и `interval_count`. Строк будет несколько на пользователя: выводятся все моменты, когда лимит был превышен, а не последний.

## Про RANGE

Основной приём здесь один. Используется `RANGE BETWEEN hours * 60 * 60 PRECEDING`, то есть интервал в секундах. `ROWS` здесь дал бы неверный результат: у одного пользователя может быть три операции в сутки, а у другого триста, и `ROWS` посчитал бы фиксированное число строк вместо фиксированного промежутка времени. Для временных рядов это разные вещи.

Интервал переведён в секунды, потому что так согласованнее с форматом `DateTime`.

## Если данных станет много

На больших объёмах стоит завести индексы на `account_id` и `operation_datetime`, а также материализованные представления для предрасчёта. При очень большом пороге может понадобиться явное приведение типа для `threshhold`.

## Про семантику вывода

Выводятся все операции в момент нарушения. Для расследования это правильный след, но для отчётности по количеству нарушителей запрос надо ещё договорить до `DISTINCT account_id`, иначе один явный нарушитель даст десятки строк.
