# Аналитика для корпоративных клиентов

PostgreSQL. Аналитика успеваемости студентов корпоративного клиента, `company_id = 1`.

## Задача

Собрать данные, по которым можно оценить прогресс студентов и понять, где программу нужно менять.

Основная сложность в том, что попытка решения фиксируется в двух системах, `coderun` и `codesubmit`. Для честного подсчёта их нужно объединять через `UNION ALL`, иначе картина по сложности задач будет систематически занижена.

## Прогресс студента

Метрика: количество завершённых задач из начатых.

Максимум по компании считается как `COUNT(DISTINCT problem_id)` по `codesubmit` с джойном на `users` по `company_id = 1`.

Лидеры компании это тот же подсчёт с `GROUP BY user_id` и сортировкой по убыванию.

Среднее по компании считается в два шага. Сначала для каждого студента количество уникальных задач, потом среднее по студентам. Плоский `AVG` по строкам дал бы среднее по всем попыткам, а не по людям, и цифра была бы другой.

Топ задач по популярности собирается так: `UNION ALL` из `coderun` и `codesubmit`, группировка по паре студент и задача, суммирование попыток по задаче, сортировка.

Задачи 135, 140, 151, 134, 123, 122, 139, 119, 146 и 137 решаются заметно чаще остальных. Это повод смотреть на формулировку условия, а не только на сложность темы.

## Сложности решения

Задачи с наибольшим числом попыток находятся тем же способом через объединённый поток. Среднее число попыток считается отдельно по `coderun` и по `codesubmit`, чтобы было видно, где основная нагрузка.

По результатам видно устойчивую картину: много попыток при малом числе успешных решений. Такие задачи попадают в кандидаты на пересмотр.

## Что из этого следует

Студенты испытывают системные сложности в отдельных темах. Часть задач требует доработки, потому что сложность завышена либо условие сформулировано неоднозначно.

## Где лежат запросы

Запросы лежат в `question.sql`, в комментариях записано, что проверяется. Похожий набор вопросов закрыт параметризованными дашбордами в Metabase, см. соседний проект.
